## Context

当前仓库中，`quartsys-fronted` 与 `quartsys-backend` 已经建立了较完整的 API 对接面，但系统仍处在“原型接入后期”状态：接口名称与调用路径大多存在，实际行为却夹杂本地端口探测、静态 fallback 运营数据、随机风控结果、单用户硬编码和内存态通知等实现。已有的 `quartsys-fronted/docs/FRONTEND_BACKEND_INTEGRATION.md` 已识别出大多数缺口，说明问题重点不在新增页面，而在让现有页面绑定到稳定、真实、可解释的数据来源。

这次变更的核心约束是现有前端 UI 不发生结构性变化，并把“后端联接稳定不出错”和“基本功能先完整可用”置于一切增强工作之前。修复工作必须主要落在 API 绑定、运行时状态、后端占位逻辑清理和错误态治理上，而不是重构页面布局或替换组件树。

## Goals / Non-Goals

**Goals:**
- 保持现有页面布局、文案结构和视觉样式不变，仅替换数据来源与状态处理方式。
- 让前端 API 联接基于显式配置和真实运行环境，而不是依赖本地回环地址自动试探。
- 让风险、通知、用户资料、Agent 生命周期、策略生成等能力返回真实结果或明确失败，不再向 UI 注入静态/随机/伪造业务数据。
- 建立“用户登录态 -> JWT -> 后端 current user -> 数据隔离”的最小闭环，消除单用户硬编码。
- 将高风险对接点纳入自动化检查和自动化回归修复范围，优先防止字段契约漂移、伪联通和回归错误。
- 按优先清理清单先打通登录、首页、风险、交易、回测、设置页的核心基础链路。

**Non-Goals:**
- 不重做页面 UI，不新增视觉组件，也不改变路由结构。
- 不在本次变更中引入实时推送、WebSocket 或复杂任务调度平台。
- 不在本次变更中追求所有量化能力“业务最优”，重点是先消除错误数据和伪联接。
- 不处理与当前 UI 无直接依赖的历史技术债。

## Decisions

### 1. UI 稳定性高于功能增强

**决策**：所有修复都必须以“现有 UI 不大改”为前提，优先替换数据绑定和状态展示，不允许通过大改页面结构来规避联接问题。

**理由**：用户明确要求视觉界面稳定。联接问题本质上属于数据契约和运行态问题，不应通过重写 UI 掩盖。

**替代方案**：借重构页面顺便修联接。该方案会显著扩大回归面，因此放弃。

### 2. 联接稳定性高于页面丰满度

**决策**：优先保证接口可用、字段正确、状态可解释；当真实数据缺失时，用空态/错误态替代示例业务数据。

**理由**：当前最大风险是页面“看起来有内容”，但内容是假的。稳定、诚实的空态比伪造数据更符合后续开发和运维目标。

**替代方案**：继续保留 fallback 让页面显得完整。该方案会持续掩盖问题，因此不采用。

### 3. 基本功能闭环优先于高级功能扩展

**决策**：先清理登录、Dashboard、Risk、Trading、Backtesting、Settings 的基础读写链路，再考虑更高阶分析能力增强。

**理由**：这些页面构成用户最直观的主流程。只要它们存在字段错位、用户错位或伪联通，新增能力没有意义。

**替代方案**：按模块平行推进。该方案会导致基础问题长期悬而未决，因此不优先。

### 4. 自动化修复意味着“自动发现 + 自动回归校验”

**决策**：将“自动化修复”定义为：关键字段契约、关键接口和关键页面状态必须有自动化校验与回归脚本支撑；能通过工具自动验证的，不依赖人工感觉判断。

**理由**：当前问题大多是“表面能跑”，人工联调很容易漏掉。只有自动化检查才能防止问题重复出现。

**替代方案**：仅靠人工联调清单。该方案无法有效防回归，因此不够。

### 5. API 基址使用显式配置优先，保留受控降级

**决策**：前端 API 基址应优先来自环境变量或运行时明确配置；对本地开发可保留受控 fallback，但不能在默认生产代码路径中内置 `127.0.0.1:8010/8000` 多级探测。

**理由**：当前自动探测逻辑会把部署环境与本地开发耦合在一起，导致“偶然能连上”和“真实配置正确”无法区分。显式配置是稳定联接的必要条件。

**替代方案**：继续保留自动轮询多个本地地址。该方案便于本地调试，但会持续掩盖配置错误，因此仅允许作为开发态专用兜底，不作为主路径。

### 6. 占位接口改为“真实结果或结构化失败”

**决策**：后端占位能力不再返回静态示例数据或随机业务值；无法即时算出真实结果时，返回结构化失败/空态，并让前端维持现有 UI 但显示可解释状态。

**理由**：随机风险值、静态事件和 `# TODO: implement` 代码片段会误导用户，也会让联调看起来“成功”但实质不可用。对现有 UI 而言，明确空态比伪数据更安全。

**替代方案**：继续使用“示例数据保证页面丰满”。该方案短期观感较好，但会掩盖真实联接问题，因此不采用。

### 7. 用户态统一通过 JWT 解出 current user

**决策**：Profile、Agent、Notification 及其后续衍生能力统一从 JWT 中解析当前用户，不再使用 `user_id=1` 或全局内存列表。

**理由**：现有 UI 已具备登录态与 token 存储，后端仍停留在单用户假设会造成跨页面数据错位，也无法支撑真实联接。

**替代方案**：继续使用默认用户，等多用户需求明确后再修。该方案会直接妨碍当前联接正确性，不满足本次目标。

### 8. 后端必须适配现有前端消费 DTO

**决策**：关键页面依赖接口由后端输出稳定、前端可直接消费的 DTO；前端仅允许做薄适配和状态展示，不通过重写页面结构、拼猜字段或引入多套业务模型来迁就后端漂移。

**理由**：用户已经明确优先级是“后端更适配前端消费的 DTO，而不是改前端风格”。如果把契约修复压力留在页面层，短期可能能跑，长期会让 UI 绑定越来越脆弱。

**替代方案**：由前端页面层做字段兼容与结构重组。该方案会扩大回归面，也违背“UI 不大改”的约束，因此不采用。

### 9. 响应语义统一为成功 / 空态 / 失败三类

**决策**：关键接口在不破坏现有页面绑定的前提下统一响应语义：
- 成功：`200` + 稳定 DTO payload
- 空态：`200` + 同形状空 payload，并附带 `status: "empty"` 或等价元信息
- 失败：`4xx/5xx` + `{ code, message, details? }`

**理由**：当前问题不是“有没有接口”，而是页面拿到随机值、示例值或静默 fallback 后无法分辨真假。统一语义后，前端可以在保持现有布局的前提下稳定处理加载、空态和错误态。

**替代方案**：每个接口各自定义空态和失败行为。该方案会迫使页面写大量特殊分支，并增加误判和回归概率，因此不采用。

### 10. 页面空态必须按现有 UI 面板逐页固化

**决策**：Dashboard、Risk、Trading、Backtesting、AI Insights、Settings 六个 P0 页面分别定义允许的空态语义，禁止用静态示例业务数据补满既有卡片、榜单、仓位、日志或推荐区域。

**理由**：这些页面是当前前后端对接最容易“表面正常、实际失真”的区域。先把页面级空态规则说清楚，后续开发才不会为了让页面“看起来完整”再次引入伪数据。

**替代方案**：只写抽象原则，不定义页面级规则。该方案会导致执行时理解分叉，因此不采用。

### 11. 自动化门禁按契约 -> 主流程冒烟 -> 页面态回归排序

**决策**：自动化检查采用固定顺序：
1. 先跑 API 字段契约测试
2. 再跑 `登录 -> Dashboard` 主流程冒烟
3. 最后跑六个关键页面的空态 / 错误态 / 鉴权失效回归检查

**理由**：字段契约是最底层依赖，主流程冒烟能快速发现联接是否断裂，页面态回归则用于防止“功能能通但展示错误”的问题。按这个顺序能最早暴露最关键的问题。

**替代方案**：所有检查平行执行、无优先级。该方案会让失败信号更噪声，也不利于快速定位问题，因此不采用。

## Risks / Trade-offs

- [Risk] 移除前端 fallback 后，部分页面会更早暴露空态 -> Mitigation: 保留现有布局，仅增强 loading/empty/error 表达，不改变视觉骨架。
- [Risk] 开发态移除多地址自动探测后，历史本地启动脚本可能立即暴露配置缺失 -> Mitigation: 保留仅开发环境可启用的显式 fallback，并同步更新 `.env.example` 与 README。
- [Risk] 风险事件、资金流向等能力短期内没有成熟数据源 -> Mitigation: 先输出基于持仓/行情的可重复计算结果，无法生成时返回空态和错误原因，而非示例数据。
- [Risk] 将通知和 profile 绑定真实用户后，现有测试数据可能无法直接复用 -> Mitigation: 补最小 seed/迁移脚本，并对匿名/无数据用户返回可显示空态。
- [Risk] Agent start/stop 从“改状态”升级为真实后台生命周期后，实现复杂度上升 -> Mitigation: 第一阶段先实现可观测任务注册、状态机和停止标记，不在本次强行引入分布式执行。
- [Risk] 自动化检查初期会暴露更多旧问题，短期看似增加工作量 -> Mitigation: 按 P0/P1/P2 分层纳入自动化，先覆盖最核心主链路。

## Migration Plan

1. 先按 P0 清理字段契约错误、API 基址收敛、JWT 用户态闭环和页面级伪联通 fallback。
2. 再按 P1 修复后端占位实现，优先顺序为 Risk / Settings / Backtesting / AI Insights / Trading 辅助面板。
3. 前端逐页切换掉 demo/fallback 数据绑定，统一接入加载、空态和错误态，并保持 UI 结构不变。
4. 为关键接口与页面状态补充自动化脚本，并按“字段契约 -> 登录到 Dashboard 冒烟 -> 六个关键页面状态回归”的顺序建立门禁。
5. 更新集成文档，补充联调检查清单，并在本地/测试环境完成端到端核对。
6. 若上线后发现真实数据源不足导致页面空置，可按 capability 维度回滚到“结构化空态”，但不回滚到静态伪数据。

## Open Questions

- 风险事件与资金流向的“真实来源”优先级如何定：优先基于现有持仓/行情推导，还是接入外部数据源（如 akshare）？
- Agent start/stop 的最小“真实执行”语义是什么：需要真实跑策略，还是先提供可观测的任务队列与状态转换？
- 通知中心是否需要按用户持久化历史消息，还是只需持久化系统内生成的操作通知？
- `src/shared/ai.ts` 中直连第三方 AI 服务的能力，是否应纳入本次“前后端完美适配”范围，还是继续作为前端直连通道保留？
